In a garbage-collected language every object hides behind a header and a pointer, and the runtime decides how it is stored. In Rust a value *is* its bytes: a `struct` of two `u32` is eight bytes, inline, wherever you put it (on the stack, inside a `Vec`, inside another struct). Knowing how the compiler lays those bytes out helps you reason about performance, FFI and some of the cleverest optimizations in the language.

## Size and alignment

Every type has two numbers, both available at compile time:

- **`size_of::<T>()`**: how many bytes a value occupies, including padding. It is always a multiple of the alignment, so that arrays of `T` stay aligned.
- **`align_of::<T>()`**: the address of a value must be a multiple of this. A `u32` wants addresses divisible by 4, a `u64` by 8 (on 64-bit targets).

<Playground title="Sizes and alignments">
```rust
use std::mem::{align_of, size_of};

#[allow(dead_code)]
struct Mixed { a: u8, b: u32, c: u16 }

#[allow(dead_code)]
#[repr(C)]
struct MixedC { a: u8, b: u32, c: u16 }

struct Marker; // zero-sized type

macro_rules! show {
    ($($t:ty),* $(,)?) => {
        $( println!("{:<20} size {:>2}  align {}", stringify!($t), size_of::<$t>(), align_of::<$t>()); )*
    };
}

fn main() {
    show!(u8, u16, u32, u64, u128, char, bool, f64);
    show!(Mixed, MixedC, Marker, (u8, u64), [u16; 3]);
}
```
</Playground>

`Mixed` and `MixedC` have the same three fields, yet one is 8 bytes and the other 12. That gap is **padding**, and who decides about it is the subject of the next section. Also notice that `char` is 4 bytes: it holds any Unicode scalar value, unlike a C `char` or a Java UTF-16 `char`.

## Field order: repr(Rust) vs repr(C)

With the default representation, `repr(Rust)`, the compiler is **free to reorder fields**. Today `rustc` essentially sorts them by decreasing alignment, which minimizes padding: `Mixed` becomes `b: u32, c: u16, a: u8` plus one byte of tail padding. With `#[repr(C)]` the fields stay in declaration order and each one is aligned in place, exactly as a C compiler would do: `a`, three bytes of padding, `b`, `c`, two bytes of tail padding.

<Callout type="warn" title="Do not rely on the default layout">
The `repr(Rust)` layout is **unspecified**. It can change between compiler versions, and two generic instantiations of the same struct may be laid out differently. Code that transmutes bytes, shares memory with C or sends structs over the wire needs `#[repr(C)]` (or `#[repr(transparent)]` for single-field wrappers). For anything else, let the compiler choose.
</Callout>

## Enums: discriminants and niches

A Rust `enum` is a tagged union: a **discriminant** says which variant is active, followed by enough space for the largest variant. That is why `Shape` below takes 12 bytes: a tag plus two `f32`. But the compiler is smarter than a naive tagged union. If a type has bit patterns that are **invalid** for it, the compiler can use them to encode the discriminant for free. These spare patterns are called **niches**.

- A reference `&T` can never be null, so `Option<&T>` uses the null pointer to mean `None`: same size as a pointer, exactly like a nullable pointer in C.
- `Box<T>`, `NonNull<T>`, `Vec<T>` and `String` contain a non-null pointer, so wrapping them in `Option` is free.
- `NonZeroU32` forbids zero, so `Option<NonZeroU32>` is 4 bytes while `Option<u32>` needs 8.
- `bool` only uses 0 and 1, leaving 254 niches: `Option<Option<bool>>` still fits in one byte.

<Playground title="Enum sizes and the niche optimization">
```rust
use std::mem::size_of;
use std::num::NonZeroU32;

#[allow(dead_code)]
enum Shape { Circle(f32), Rect(f32, f32), Empty }

#[allow(dead_code)]
#[repr(u8)]
enum Status { Ok = 0, NotFound = 4, Teapot = 18 }

macro_rules! show {
    ($($t:ty),* $(,)?) => { $( println!("{:<24} {:>2} bytes", stringify!($t), size_of::<$t>()); )* };
}

fn main() {
    show!(Shape, Status, Option<u32>, Option<NonZeroU32>);
    // niche optimization: the "impossible" bit pattern encodes None
    show!(&u64, Option<&u64>, Box<u64>, Option<Box<u64>>, bool, Option<bool>, Option<Option<bool>>);
    show!(Result<u32, ()>, Option<String>, Option<Vec<u8>>);
    println!("Status::Teapot as u8 = {}", Status::Teapot as u8);
}
```
</Playground>

<Callout type="compare" from="Java / C#">
In Java an `Optional<Integer>` is a heap object pointing to another heap object. In Rust `Option<NonZeroU32>` is four bytes on the stack, and `Option<&T>` compiles to exactly the same machine code as a nullable pointer check. "No null" costs nothing because the compiler reuses the representation null would have had.
</Callout>

## Fat pointers

Most references are a single machine word. Two kinds carry an extra word of metadata and are called **fat pointers**:

| Type | Words | Contents |
| --- | --- | --- |
| `&T`, `Box<T>` (sized `T`) | 1 | address |
| `&[T]`, `&str`, `Box<[T]>` | 2 | address + length |
| `&dyn Trait`, `Box<dyn Trait>` | 2 | data address + vtable address |
| `Vec<T>`, `String` | 3 | heap pointer + length + capacity |

<Playground title="Looking inside Vec, slices, &str and &dyn">
```rust
use std::fmt::Debug;
use std::mem::size_of_val;

fn main() {
    let v: Vec<u32> = vec![10, 20, 30, 40];
    println!("{:<10} {:>2} bytes  ptr={:p} len={} cap={}", "Vec<u32>", size_of_val(&v), v.as_ptr(), v.len(), v.capacity());

    // A slice reference is a fat pointer: (ptr, len)
    let s: &[u32] = &v[1..3];
    println!("{:<10} {:>2} bytes  ptr={:p} len={}", "&[u32]", size_of_val(&s), s.as_ptr(), s.len());

    // &str is a slice of UTF-8 bytes: len counts bytes, not characters
    let text = "perché";
    println!("{:<10} {:>2} bytes  len={} chars={}", "&str", size_of_val(&text), text.len(), text.chars().count());

    // &dyn Trait is (data ptr, vtable ptr)
    let d: &dyn Debug = &v;
    println!("{:<10} {:>2} bytes  data ptr + vtable ptr", "&dyn Debug", size_of_val(&d));
}
```
</Playground>

The slice's pointer is the `Vec`'s pointer plus 4 bytes: slicing does not copy, it just builds a new `(ptr, len)` pair pointing into the same buffer. A `String` is literally a `Vec<u8>` that guarantees UTF-8, and `&str` is a `&[u8]` with the same guarantee, which is why `len()` counts bytes.

<Callout type="runtime">
There is no object header in Rust. A Java object carries a mark word and a class pointer (12–16 bytes) before its first field; a Python `int` is 28 bytes. A Rust `u32` is 4 bytes and a `Vec<u32>` with one million elements is 24 bytes on the stack plus exactly 4 MB on the heap. Dynamic dispatch information lives in the *pointer* (`&dyn Trait`), not in the value, so you pay for it only where you use it.
</Callout>

## Zero-sized types

A struct with no fields, `()`, `PhantomData<T>` or an empty array have size zero. They exist only in the type system:

- `HashSet<T>` is implemented as `HashMap<T, ()>`: the values take no space at all.
- A `Vec<()>` never allocates; pushing just increments the length.
- Marker types such as `struct Meters;` or typestate parameters (`Connection<Open>`) cost nothing at runtime.

Zero-sized types are one of the reasons "zero-cost abstraction" is meant literally: types can encode rules the compiler checks, and then disappear completely from the binary.

## Key takeaways

- A Rust value is its bytes, stored inline with no header; `size_of` and `align_of` are compile-time constants.
- Padding keeps fields aligned. With the default `repr(Rust)` the compiler reorders fields to reduce it, but the exact layout is unspecified.
- Use `#[repr(C)]` for FFI and any code that depends on byte layout.
- Enums are tagged unions, and niches let `Option<&T>`, `Option<Box<T>>` and `Option<NonZeroU32>` cost nothing extra.
- Slices and `&str` are (pointer, length); `&dyn Trait` is (pointer, vtable); `Vec` and `String` are (pointer, length, capacity).
- Zero-sized types carry information in the type system and vanish from the compiled code.
