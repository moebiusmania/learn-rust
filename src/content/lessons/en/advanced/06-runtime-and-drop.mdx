"Rust has no runtime" is a useful slogan and a slightly wrong statement. There is no garbage collector, no virtual machine, no scheduler and no reflection. But every Rust binary still carries a few hundred lines of support code, and the most important piece of "runtime behaviour" is not code you link at all: it is the **destructor calls the compiler inserts** for you. This lesson looks at both.

## What runs before main

When the OS starts a Rust executable, it does not jump straight into your `main`. The C runtime calls the real entry point generated by `rustc`, which calls `std::rt::lang_start`. Roughly:

1. Store `argc`/`argv` so `std::env::args()` can read them later.
2. On Unix, install a **stack-overflow guard**: a protected page plus a signal handler, so overflowing the stack prints a clear message instead of corrupting memory.
3. Set up the main thread's name and thread-local storage.
4. Call your `main`, inside a boundary that catches a panic escaping from it.
5. Turn the result into an exit code: `0` on success, `1` if `main` returns an `Err` (it may return a `Result`), or `101` after a panic.

Compare that with the startup of the JVM, the .NET CLR or the Node.js event loop. There is no class loading, no JIT warm-up and no heap to size: a Rust binary is ready to work in microseconds.

<Callout type="runtime">
The remaining "runtime" pieces are: the **global allocator** (by default the system `malloc`/`free`, replaceable with `#[global_allocator]`), the **panic machinery** (the panic hook that prints the message and, with unwinding, the tables and personality routine that walk the stack), and whatever thread-local and synchronization primitives `std` uses on your platform. Async executors, green threads and garbage collection are libraries you opt into, not part of the language.
</Callout>

You can replace the allocator with ten lines of code. This one wraps the system allocator and counts calls, which makes it easy to see which operations touch the heap:

<Playground title="A counting global allocator">
```rust
use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering};

/// Wraps the system allocator and counts every allocation.
struct Counting;

static ALLOCATIONS: AtomicUsize = AtomicUsize::new(0);

unsafe impl GlobalAlloc for Counting {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        ALLOCATIONS.fetch_add(1, Ordering::Relaxed);
        unsafe { System.alloc(layout) }
    }
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) {
        unsafe { System.dealloc(ptr, layout) }
    }
}

#[global_allocator]
static GLOBAL: Counting = Counting;

fn count<T>(label: &str, f: impl FnOnce() -> T) -> T {
    let before = ALLOCATIONS.load(Ordering::Relaxed);
    let value = f();
    let after = ALLOCATIONS.load(Ordering::Relaxed);
    println!("{label:<28} {} allocation(s)", after - before);
    value
}

fn main() {
    count("integer arithmetic", || 6 * 7);
    count("array on the stack", || [0u64; 1024]);
    count("Vec::with_capacity(1000)", || Vec::<u64>::with_capacity(1000));
    count("collect 1000 items", || (0..1000u64).collect::<Vec<_>>());
    count("format! a String", || format!("{} items", 1000));
}
```
</Playground>

Projects swap in allocators such as jemalloc or mimalloc this way for throughput, and embedded code provides its own on top of a fixed memory region.

## RAII: destructors you never call

Rust uses **RAII** (Resource Acquisition Is Initialization), the idea C++ made famous: a value that owns a resource releases it in its destructor, and the destructor runs automatically when the owner goes out of scope. In Rust the destructor is the `Drop` trait:

```rust
impl Drop for Connection {
    fn drop(&mut self) {
        self.socket.shutdown();
    }
}
```

`Vec`, `String`, `Box`, `File`, `MutexGuard`, `TcpStream`: all of them free memory, close handles or release locks in `drop`. Because ownership is tracked statically, the compiler knows exactly where each value dies and inserts the call there. There is no finalizer queue and no "eventually".

<Compare left="Java / Python">
```java
// try-with-resources: only for AutoCloseable,
// only if the caller remembers to use it
try (var file = new FileReader("data.txt")) {
    process(file);
} // file.close() here

// Without it, the GC *may* finalize the object
// at some unspecified later time.
```

```rust
// Every owning value is a "resource".
{
    let file = File::open("data.txt")?;
    process(&file);
} // file dropped (closed) here, always

// Early return, `?`, or a panic that unwinds:
// the close still happens, in a known order.
```
</Compare>

## The drop order rules

Since destructors can have observable effects (printing, flushing, unlocking), Rust specifies their order precisely:

1. **Local variables** are dropped at the end of their scope in **reverse order of declaration**: last created, first destroyed. A later variable may borrow an earlier one, so it must go first.
2. A value's own `Drop::drop` runs **before** its fields are dropped, so the destructor can still use them.
3. **Struct fields** are then dropped in **declaration order** (not reversed). Tuple and array elements likewise, front to back, and so are the elements of a `Vec`.
4. **Temporaries** created inside an expression statement are dropped at the end of that statement, at the `;`.
5. A **moved-out** value is not dropped at the old location; whoever owns it now is responsible.

## Panics: unwind or abort

A panic signals a **bug**: an index out of bounds, an `unwrap()` on `None`, a failed assertion. Recoverable failures belong in `Result`. When a panic happens, the default strategy is **unwinding**: the panic hook prints the message, then the runtime walks back up the call stack, running every destructor in every frame, until it reaches the thread boundary. For the main thread, that ends the process with exit code 101.

<Playground title="Destructors run during unwinding">
```rust
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn inner() {
    let _g = Noisy("inner guard");
    panic!("boom");
}

fn main() {
    let _m = Noisy("main guard");
    inner();
    println!("never printed");
}
```
</Playground>

Unwinding is why a `MutexGuard` still releases its lock and a `BufWriter` still flushes when something goes wrong. It has a cost: the compiler emits **landing pads** and unwind tables for every function that owns values with destructors. In `Cargo.toml` you can choose the alternative:

```toml
[profile.release]
panic = "abort"   # no unwinding: print the message and kill the process
```

With `abort`, binaries get smaller and code slightly tighter, but destructors do not run on panic and `std::panic::catch_unwind` no longer catches anything. Many servers keep unwinding so a panic in one request handler (on its own thread or task) does not take the whole process down; many CLIs and embedded targets choose abort.

<Callout type="warn" title="catch_unwind is not try/catch">
`std::panic::catch_unwind` exists to stop a panic at an FFI boundary (unwinding into C is undefined behaviour) or at the edge of a thread pool. It is not an exception mechanism: it only works with `panic = "unwind"`, and code that relies on it for control flow will silently change behaviour when someone switches to abort.
</Callout>

## Controlling destruction yourself

Sometimes you need to end a value's life earlier, or never:

<Playground title="drop, forget, ManuallyDrop, leak">
```rust
use std::mem::ManuallyDrop;
use std::panic;

struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn main() {
    let _ = Noisy("underscore");      // `_` does not bind: dropped right here
    let _kept = Noisy("_kept");       // `_kept` is a binding: lives to the end
    let len = Noisy("temporary").0.len(); // temporary dropped at the `;`
    println!("len = {len}");

    let early = Noisy("early");
    drop(early);                      // std::mem::drop just takes ownership

    std::mem::forget(Noisy("forgotten"));          // destructor never runs
    let _manual = ManuallyDrop::new(Noisy("manual")); // same, as a wrapper type

    let leaked: &'static mut Vec<i32> = Box::leak(Box::new(vec![1, 2, 3]));
    leaked.push(4);
    println!("leaked = {leaked:?}");

    let result = panic::catch_unwind(|| {
        let _guard = Noisy("guard");
        panic!("boom");
    });
    println!("caught a panic: {}", result.is_err());
    println!("end of main");
}
```
</Playground>

- `drop(x)` is not magic: `std::mem::drop` is an empty function that takes ownership, so the value dies when the function returns. Use it to release a lock or close a file before the end of the scope.
- `let _ = expr;` **does not bind**, so the value is dropped immediately. `let _guard = expr;` binds and keeps it alive. Confusing the two is a classic bug with lock guards.
- `std::mem::forget` and `ManuallyDrop` skip the destructor. Both are safe: leaking memory is not a memory-safety violation, just usually a mistake. `ManuallyDrop` is the tool of choice inside `unsafe` data structures.
- `Box::leak` gives up ownership on purpose and returns a `&'static mut`. It is a legitimate way to create global configuration that lives for the whole program.

You cannot call `x.drop()` directly; the compiler rejects it, precisely so a value is never destroyed twice.

## no_std: removing the runtime entirely

For microcontrollers, kernels, bootloaders and WebAssembly modules, a crate can opt out of the standard library with `#![no_std]`. It then links only **core** (types, traits, iterators, `Option`, `Result`, slices: everything that needs no operating system) and, optionally, **alloc** (`Vec`, `String`, `Box`) once you provide a global allocator.

```rust
#![no_std]
#![no_main]

use core::panic::PanicInfo;

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    loop {} // e.g. blink an LED, reset the chip
}
```

In a `no_std` binary you write the panic handler yourself and the entry point comes from your hardware support crate. Ownership, borrowing, traits and `Drop` all work exactly the same, which is a large part of why Rust is gaining ground in embedded systems where C has ruled for decades.

## Key takeaways

- A Rust binary carries a tiny runtime: a startup routine, the global allocator and the panic machinery. No GC, no VM, no reflection.
- RAII via `Drop` releases memory, files and locks at a point fixed by the source code.
- Locals drop in reverse declaration order; a value's `Drop::drop` runs before its fields, which drop in declaration order; temporaries drop at the end of the statement.
- Panics unwind by default and run destructors along the way; `panic = "abort"` trades that for smaller, slightly faster binaries.
- `drop`, `forget`, `ManuallyDrop` and `Box::leak` give explicit control; `let _ =` drops immediately.
- `#![no_std]` keeps the language and `core` while removing the operating-system-dependent runtime.
