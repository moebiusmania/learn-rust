Three types cover most everyday data in Rust: `Vec<T>`, `String` and `HashMap<K, V>`. None of them is special: they are ordinary library structs that own a heap buffer, so everything you learned about ownership and borrowing applies to them unchanged. What changes is how much of their memory behaviour you can now *see*.

## Vec: a growable array

A `Vec<T>` is three words on the stack: a **pointer** to a heap buffer, the **length** (how many elements are initialized) and the **capacity** (how many fit before the buffer must grow). When `len` reaches `capacity`, `push` allocates a bigger buffer, moves the elements, and frees the old one. Try it:

<VecGrowth />

Doubling the capacity makes `push` *amortized* O(1): the total cost of all the copies stays proportional to the number of elements. If you know the final size, `Vec::with_capacity(n)` avoids reallocations altogether.

<Playground title="Vec, capacity and slices">
```rust
fn sum(values: &[i32]) -> i32 {
    values.iter().sum()
}

fn main() {
    let mut v: Vec<i32> = Vec::with_capacity(4);
    for n in [3, 1, 4, 1, 5, 9] {
        v.push(n);
        println!("push {n}: len={} capacity={}", v.len(), v.capacity());
    }

    // A slice is a borrowed view (pointer + length) into contiguous memory
    let middle: &[i32] = &v[1..4];
    println!("middle = {middle:?}, sum = {}", sum(middle));
    println!("whole sum = {}", sum(&v)); // &Vec<i32> coerces to &[i32]
    let array = [10, 20, 30];
    println!("array sum = {}", sum(&array)); // so does &[i32; 3]

    v.sort();
    v.dedup();
    println!("sorted and deduplicated: {v:?}");
    println!("first = {:?}, get(99) = {:?}", v.first(), v.get(99));
}
```
</Playground>

### Slices: borrowed views

`&[T]` is a **slice**: a pointer plus a length, borrowing a contiguous run of `T` that someone else owns. `&v[1..4]` borrows part of a vector, `&v` borrows all of it, and arrays coerce the same way. A function that only reads a sequence should take `&[T]`, not `&Vec<T>`: it then accepts vectors, arrays and sub-ranges alike, at no cost.

<Callout type="runtime" title="Why a push can invalidate references">
A reallocation *moves* the elements to a new address. Any reference into the old buffer would now point to freed memory, which in C++ is the classic iterator-invalidation bug. In Rust, holding a `&` into a `Vec` borrows the whole `Vec`, and `push` needs `&mut self`, so the two cannot overlap. The compiler rejects the bug before it exists:
</Callout>

<Playground title="Modifying a Vec while iterating over it" expectError>
```rust
fn main() {
    let mut scores = vec![10, 20, 30];
    for score in &scores {
        if *score == 20 {
            scores.push(25); // grow the Vec while iterating over it
        }
    }
    println!("{scores:?}");
}
```
</Playground>

<Callout type="compare" from="Java / C++">
Java detects this at runtime with a `ConcurrentModificationException`, when the loop happens to run. C++ does not detect it at all: it is undefined behaviour. Rust reports it at compile time as an ordinary borrow error (E0502). The fix is to collect changes first and apply them after the loop, or use methods such as `retain`, `extend` or `iter().position()`.
</Callout>

## String and &str

Rust has two main string types, and the split mirrors `Vec<T>` and `&[T]`:

| Type | What it is | Owns its data | Typical use |
| --- | --- | --- | --- |
| `String` | A `Vec<u8>` guaranteed to hold valid UTF-8 | Yes | Building and storing text |
| `&str` | A slice of UTF-8 bytes (pointer + length) | No | Reading text, function parameters |
| `&'static str` | A `&str` pointing into the binary itself | No | String literals like `"hello"` |
| `char` | One Unicode scalar value, always 4 bytes | — | Single characters |

As with slices, prefer `&str` for parameters: a `&String` coerces to `&str` automatically, and so does a literal.

<Playground title="String, &str and UTF-8">
```rust
fn main() {
    let owned: String = String::from("Caffè"); // heap, growable, owned
    let literal: &str = "naïve 🦀";            // borrowed, stored in the binary
    let slice: &str = &owned[0..4];             // borrowed view into `owned`

    println!("{owned:?}: {} bytes, {} chars", owned.len(), owned.chars().count());
    println!("{literal:?}: {} bytes, {} chars", literal.len(), literal.chars().count());
    println!("slice = {slice:?}");

    // Iterate by char (Unicode scalar value), with byte offsets
    for (offset, c) in literal.char_indices() {
        print!("{offset}:{c} ");
    }
    println!();
    println!("bytes of 'è': {:x?}", "è".as_bytes());

    // Building strings
    let mut s = String::new();
    s.push_str("Hello");
    s.push(',');
    s += " world";
    let shout = format!("{}!", s.to_uppercase());
    println!("{shout}");

    // &owned[0..5] would panic: byte 5 is in the middle of 'è'
}
```
</Playground>

### Why s[0] does not compile

In most languages `s[0]` returns "the first character". In Rust this is a compile error:

```rust
let s = String::from("hey");
let c = s[0]; // error[E0277]: the type `str` cannot be indexed by `{integer}`
```

The reason is that strings are UTF-8, a variable-width encoding: `è` is 2 bytes, `🦀` is 4. "The character at index 5" cannot be found in O(1), and "character" is ambiguous anyway: byte, Unicode scalar value, or user-perceived grapheme (an emoji with a skin-tone modifier is several scalar values)? Rust makes you say which one you mean:

- `s.as_bytes()[i]` for bytes, O(1).
- `s.chars().nth(i)` for Unicode scalar values, O(n).
- `&s[a..b]` for a substring by **byte** range, which panics if `a` or `b` falls in the middle of a character.
- Graphemes need a crate such as `unicode-segmentation`.

<Callout type="compare" from="JavaScript / Python / Java">
JavaScript and Java strings are UTF-16 internally, so `"🦀".length` is 2 and indexing can split a character in half. Python 3 picks a fixed-width representation per string (1, 2 or 4 bytes per code point) to make indexing O(1), at the cost of memory and conversions. Rust stores UTF-8 everywhere, the same encoding as files and the network, and moves the cost to the rare places where you really need positional access.
</Callout>

## HashMap and the entry API

`HashMap<K, V>` lives in `std::collections` and works with any key type that implements `Eq` and `Hash` (derivable for your own types). Lookups return `Option<&V>` instead of `null` or a `KeyError`. The **entry API** handles the "insert if missing, then update" pattern with a single hash lookup, and without the double-borrow problem you would hit doing `get` followed by `insert`.

<Playground title="Counting words with entry">
```rust
use std::collections::HashMap;

fn main() {
    let text = "the quick brown fox jumps over the lazy dog the end";
    let mut counts: HashMap<&str, usize> = HashMap::new();
    for word in text.split_whitespace() {
        // entry: one lookup to find-or-insert, then mutate in place
        *counts.entry(word).or_insert(0) += 1;
    }

    let mut ranked: Vec<(&str, usize)> = counts.into_iter().collect();
    ranked.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0)));
    println!("top 3: {:?}", &ranked[..3]);

    let mut stock = HashMap::from([("apples", 3), ("pears", 0)]);
    stock.insert("plums", 7);
    if let Some(n) = stock.get_mut("pears") {
        *n += 5;
    }
    println!("pears: {:?}, kiwis: {:?}", stock.get("pears"), stock.get("kiwis"));

    stock.entry("kiwis").or_insert(12);
    let mut keys: Vec<_> = stock.keys().collect();
    keys.sort(); // HashMap iteration order is unspecified
    println!("{keys:?}");
}
```
</Playground>

Two defaults worth knowing: iteration order is **unspecified** (it changes between runs), and the default hasher, SipHash 1-3, is chosen to resist hash-flooding attacks rather than for raw speed. Use `BTreeMap` when you need sorted keys, and a faster hasher such as `ahash` or `rustc-hash` when keys are not attacker-controlled.

## Three ways to iterate

A `for` loop calls `IntoIterator` on what you give it, and the form you choose decides what each element is:

| Loop | Element type | Effect on the collection |
| --- | --- | --- |
| `for x in &v` | `&T` | Borrowed, unchanged, usable afterwards |
| `for x in &mut v` | `&mut T` | Borrowed exclusively, elements can be modified |
| `for x in v` | `T` | Moved: the collection is consumed |

<Playground title="By reference, by mutable reference, by value">
```rust
fn main() {
    let mut names = vec![String::from("ada"), String::from("grace"), String::from("linus")];

    for name in &names {
        // &String: shared borrow, read-only
        print!("{name} ");
    }
    println!();

    for name in &mut names {
        // &mut String: exclusive borrow, modify in place
        name.make_ascii_uppercase();
    }

    for name in names {
        // String: takes ownership, the Vec is consumed
        println!("owned {name} ({} bytes)", name.len());
    }
    // println!("{names:?}"); // error[E0382]: borrow of moved value: `names`
}
```
</Playground>

Iterating by value is not a performance trap: it moves each `String` out without copying its heap buffer, then frees the vector's own buffer at the end. It is the right choice when you are transforming one collection into another and no longer need the original.

## Key takeaways

- `Vec<T>` is pointer, length and capacity; growth doubles the buffer and moves the elements, so `push` is amortized O(1).
- Take `&[T]` and `&str` as parameters: they accept every owner of contiguous data.
- The borrow checker turns iterator invalidation into a compile-time error.
- `String` is owned UTF-8; `&str` is a borrowed slice of it. Integer indexing is not allowed because UTF-8 is variable-width.
- `HashMap` lookups return `Option`; the entry API inserts-or-updates with one lookup. Iteration order is unspecified.
- `&v`, `&mut v` and `v` in a `for` loop give you `&T`, `&mut T` and `T` respectively.
