Three types cover most everyday data in Rust: <Term id="vec">`Vec<T>`</Term>, <Term id="string">`String`</Term> and <Term id="hashmap">`HashMap<K, V>`</Term>. None of them is special: they are ordinary library <Term id="struct">structs</Term> that own a <Term id="heap">heap</Term> buffer, so everything you learned about <Term id="ownership">ownership</Term> and <Term id="borrow">borrowing</Term> applies to them unchanged. What changes is how much of their memory behaviour you can now *see*.

## Vec: a growable array

A `Vec<T>` is three words on the <Term id="stack">stack</Term>: a **pointer** to a heap buffer, the **length** (how many elements are initialized) and the **<Term id="capacity">capacity</Term>** (how many fit before the buffer must grow). When `len` reaches `capacity`, `push` allocates a bigger buffer, moves the elements, and frees the old one. Try it:

<VecGrowth />

Doubling the capacity makes `push` *<Term id="amortized">amortized</Term>* O(1): the total cost of all the copies stays proportional to the number of elements. If you know the final size, `Vec::with_capacity(n)` avoids <Term id="reallocation">reallocations</Term> altogether.

<Playground title="Vec, capacity and slices">
```rust
fn sum(values: &[i32]) -> i32 {
    values.iter().sum()
}

fn main() {
    let mut v: Vec<i32> = Vec::with_capacity(4);
    for n in [3, 1, 4, 1, 5, 9] {
        v.push(n);
        println!("push {n}: len={} capacity={}", v.len(), v.capacity());
    }

    // A slice is a borrowed view (pointer + length) into contiguous memory
    let middle: &[i32] = &v[1..4];
    println!("middle = {middle:?}, sum = {}", sum(middle));
    println!("whole sum = {}", sum(&v)); // &Vec<i32> coerces to &[i32]
    let array = [10, 20, 30];
    println!("array sum = {}", sum(&array)); // so does &[i32; 3]

    v.sort();
    v.dedup();
    println!("sorted and deduplicated: {v:?}");
    println!("first = {:?}, get(99) = {:?}", v.first(), v.get(99));
}
```
</Playground>

### Slices: borrowed views

`&[T]` is a **<Term id="slice">slice</Term>**: a pointer plus a length, borrowing a contiguous run of `T` that someone else owns. `&v[1..4]` borrows part of a vector, `&v` borrows all of it, and <Term id="array">arrays</Term> coerce the same way. A function that only reads a sequence should take `&[T]`, not `&Vec<T>`: it then accepts vectors, arrays and sub-ranges alike, at no cost.

<Callout type="runtime" title="Why a push can invalidate references">
A reallocation *moves* the elements to a new address. Any <Term id="reference">reference</Term> into the old buffer would now point to freed memory, which in C++ is the classic <Term id="iterator-invalidation">iterator-invalidation</Term> bug. In Rust, holding a <Term id="shared-reference">`&`</Term> into a `Vec` borrows the whole `Vec`, and `push` needs <Term id="mutable-reference">`&mut self`</Term>, so the two cannot overlap. The compiler rejects the bug before it exists:
</Callout>

<Playground title="Modifying a Vec while iterating over it" expectError>
```rust
fn main() {
    let mut scores = vec![10, 20, 30];
    for score in &scores {
        if *score == 20 {
            scores.push(25); // grow the Vec while iterating over it
        }
    }
    println!("{scores:?}");
}
```
</Playground>

<Callout type="compare" from="Java / C++">
Java detects this at runtime with a `ConcurrentModificationException`, when the loop happens to run. C++ does not detect it at all: it is <Term id="ub">undefined behaviour</Term>. Rust reports it at compile time as an ordinary borrow error (E0502). The fix is to collect changes first and apply them after the loop, or use <Term id="method">methods</Term> such as `retain`, `extend` or `iter().position()`.
</Callout>

## String and &str

Rust has two main string types, and the split mirrors `Vec<T>` and `&[T]`:

| Type | What it is | Owns its data | Typical use |
| --- | --- | --- | --- |
| `String` | A `Vec<u8>` guaranteed to hold valid <Term id="utf-8">UTF-8</Term> | Yes | Building and storing text |
| <Term id="str">`&str`</Term> | A slice of UTF-8 bytes (pointer + length) | No | Reading text, function parameters |
| <Term id="static-lifetime">`&'static str`</Term> | A `&str` pointing into the binary itself | No | <Term id="string-literal">String literals</Term> like `"hello"` |
| <Term id="char">`char`</Term> | One <Term id="unicode-scalar-value">Unicode scalar value</Term>, always 4 bytes | — | Single characters |

As with slices, prefer `&str` for parameters: a `&String` <Term id="deref-coercion">coerces</Term> to `&str` automatically, and so does a literal.

<Playground title="String, &str and UTF-8">
```rust
fn main() {
    let owned: String = String::from("Caffè"); // heap, growable, owned
    let literal: &str = "naïve 🦀";            // borrowed, stored in the binary
    let slice: &str = &owned[0..4];             // borrowed view into `owned`

    println!("{owned:?}: {} bytes, {} chars", owned.len(), owned.chars().count());
    println!("{literal:?}: {} bytes, {} chars", literal.len(), literal.chars().count());
    println!("slice = {slice:?}");

    // Iterate by char (Unicode scalar value), with byte offsets
    for (offset, c) in literal.char_indices() {
        print!("{offset}:{c} ");
    }
    println!();
    println!("bytes of 'è': {:x?}", "è".as_bytes());

    // Building strings
    let mut s = String::new();
    s.push_str("Hello");
    s.push(',');
    s += " world";
    let shout = format!("{}!", s.to_uppercase());
    println!("{shout}");

    // &owned[0..5] would panic: byte 5 is in the middle of 'è'
}
```
</Playground>

### Why s[0] does not compile

In most languages `s[0]` returns "the first character". In Rust this is a compile error:

```rust
let s = String::from("hey");
let c = s[0]; // error[E0277]: the type `str` cannot be indexed by `{integer}`
```

The reason is that strings are UTF-8, a variable-width encoding: `è` is 2 bytes, `🦀` is 4. "The character at index 5" cannot be found in O(1), and "character" is ambiguous anyway: byte, Unicode scalar value, or user-perceived <Term id="grapheme">grapheme</Term> (an emoji with a skin-tone modifier is several scalar values)? Rust makes you say which one you mean:

- `s.as_bytes()[i]` for bytes, O(1).
- `s.chars().nth(i)` for Unicode scalar values, O(n).
- `&s[a..b]` for a substring by **byte** range, which <Term id="panic">panics</Term> if `a` or `b` falls in the middle of a character.
- Graphemes need a <Term id="crate">crate</Term> such as `unicode-segmentation`.

<Callout type="compare" from="JavaScript / Python / Java">
JavaScript and Java strings are <Term id="utf-16">UTF-16</Term> internally, so `"🦀".length` is 2 and indexing can split a character in half. Python 3 picks a fixed-width representation per string (1, 2 or 4 bytes per code point) to make indexing O(1), at the cost of memory and conversions. Rust stores UTF-8 everywhere, the same encoding as files and the network, and moves the cost to the rare places where you really need positional access.
</Callout>

## HashMap and the entry API

`HashMap<K, V>` lives in `std::collections` and works with any key type that implements `Eq` and `Hash` (<Term id="derive">derivable</Term> for your own types). Lookups return <Term id="option">`Option<&V>`</Term> instead of `null` or a `KeyError`. The **<Term id="entry-api">entry API</Term>** handles the "insert if missing, then update" pattern with a single hash lookup, and without the double-borrow problem you would hit doing `get` followed by `insert`.

<Playground title="Counting words with entry">
```rust
use std::collections::HashMap;

fn main() {
    let text = "the quick brown fox jumps over the lazy dog the end";
    let mut counts: HashMap<&str, usize> = HashMap::new();
    for word in text.split_whitespace() {
        // entry: one lookup to find-or-insert, then mutate in place
        *counts.entry(word).or_insert(0) += 1;
    }

    let mut ranked: Vec<(&str, usize)> = counts.into_iter().collect();
    ranked.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0)));
    println!("top 3: {:?}", &ranked[..3]);

    let mut stock = HashMap::from([("apples", 3), ("pears", 0)]);
    stock.insert("plums", 7);
    if let Some(n) = stock.get_mut("pears") {
        *n += 5;
    }
    println!("pears: {:?}, kiwis: {:?}", stock.get("pears"), stock.get("kiwis"));

    stock.entry("kiwis").or_insert(12);
    let mut keys: Vec<_> = stock.keys().collect();
    keys.sort(); // HashMap iteration order is unspecified
    println!("{keys:?}");
}
```
</Playground>

Two defaults worth knowing: iteration order is **unspecified** (it changes between runs), and the default <Term id="hasher">hasher</Term>, SipHash 1-3, is chosen to resist <Term id="hash-flooding">hash-flooding</Term> attacks rather than for raw speed. Use <Term id="btreemap">`BTreeMap`</Term> when you need sorted keys, and a faster hasher such as `ahash` or `rustc-hash` when keys are not attacker-controlled.

## Three ways to iterate

A `for` loop calls <Term id="into-iterator">`IntoIterator`</Term> on what you give it, and the form you choose decides what each element is:

| Loop | Element type | Effect on the collection |
| --- | --- | --- |
| `for x in &v` | `&T` | Borrowed, unchanged, usable afterwards |
| `for x in &mut v` | `&mut T` | Borrowed exclusively, elements can be modified |
| `for x in v` | `T` | <Term id="move">Moved</Term>: the collection is consumed |

<Playground title="By reference, by mutable reference, by value">
```rust
fn main() {
    let mut names = vec![String::from("ada"), String::from("grace"), String::from("linus")];

    for name in &names {
        // &String: shared borrow, read-only
        print!("{name} ");
    }
    println!();

    for name in &mut names {
        // &mut String: exclusive borrow, modify in place
        name.make_ascii_uppercase();
    }

    for name in names {
        // String: takes ownership, the Vec is consumed
        println!("owned {name} ({} bytes)", name.len());
    }
    // println!("{names:?}"); // error[E0382]: borrow of moved value: `names`
}
```
</Playground>

Iterating by value is not a performance trap: it moves each `String` out without copying its heap buffer, then frees the vector's own buffer at the end. It is the right choice when you are transforming one collection into another and no longer need the original.

## Building toward the project

The `summary` command of `ledger` is a word-count problem in disguise: instead of counting words, it adds up amounts per category. Everything it needs is in this lesson: `lines()` and `splitn` to read the data file, a `HashMap` with the entry API to accumulate the totals, and `sort_by` to order the result, since the map's iteration order is unspecified.

<Playground title="ledger: totals per category">
```rust
use std::collections::HashMap;

fn main() {
    // The ledger data file: cents,category,note (the note may contain commas)
    let file = "1250,food,lunch, with Ada\n4500,transport,monthly pass\n820,food,coffee beans\n";

    let mut totals: HashMap<&str, i64> = HashMap::new();
    for line in file.lines() {
        let mut fields = line.splitn(3, ','); // at most 3 fields
        let cents: i64 = fields.next().unwrap().parse().unwrap();
        let category = fields.next().unwrap(); // &str borrowed from `file`
        let note = fields.next().unwrap_or("");
        println!("{cents:>6}  {category:<10} {note}");
        *totals.entry(category).or_insert(0) += cents;
    }

    let mut rows: Vec<(&str, i64)> = totals.into_iter().collect();
    rows.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0))); // largest first, then by name
    println!("{rows:?}");
}
```
</Playground>

Notice the key type: `HashMap<&str, i64>`. The keys borrow from the text instead of being copied into new `String`s. `splitn(3, ',')` stops after the second comma, so a note may contain commas of its own. The `unwrap()` calls are acceptable in a sketch; the final program replaces them with the error handling from the previous lesson, and reports the line number of a corrupted entry.

## Key takeaways

- `Vec<T>` is pointer, length and capacity; growth doubles the buffer and moves the elements, so `push` is amortized O(1).
- Take `&[T]` and `&str` as parameters: they accept every owner of contiguous data.
- The borrow checker turns iterator invalidation into a compile-time error.
- `String` is owned UTF-8; `&str` is a borrowed slice of it. Integer indexing is not allowed because UTF-8 is variable-width.
- `HashMap` lookups return `Option`; the entry API inserts-or-updates with one lookup. Iteration order is unspecified.
- `&v`, `&mut v` and `v` in a `for` loop give you `&T`, `&mut T` and `T` respectively.
